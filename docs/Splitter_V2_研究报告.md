## 0. 核心结论（先说答案）

1. **当前 splitter 不是"算法不行"，是"信号选错了"。**
   实测 133 份真实讲义：T1（目录）只命中 **9.0%**，T2-1（【题型】）**13.5%**，而 **72.9%** 的文档落在一个 2026-06-29 之后就再没动过、零测试的手调打分启发式（T2-3 评分边界）上。
2. **排版信号被管线第一步就丢掉了。**
   `app/docutils.py:62` 的 `scan_paragraphs` 只返回 `(序号, 文本, 含图)`。样式、字号、加粗、大纲级别、编号全部丢弃。
   而实测：**可用字号标题层覆盖 56.3%**（目录仅 16.6%、【题型】仅 15.3%），**短且加粗覆盖 79.9%**。
3. **用户记忆中的"稳定 0.8"找到了，但它不是一个更好的算法，而是 V0.9 的 TOC 模块，且它的改进版已经在当前仓库里。**
   `讲义生成器V0.8/` 目录内容 = V0.9 发布内容（md5 一致），真正的 V0.8 zip 里**根本没有** `toc_split.py`。V0.4 连分块模块都没有，只有 50/85 比例硬切。
4. **质量现状：第一刀还行，第二刀基本靠猜。**
   111 份实测：边界1（知识→训练）落在真实结构锚点 ±3 段内 **63.1%**，边界2（训练→巩固）**14.4%**，两刀都准 **14.4%**。
5. **最严重的结构性问题不是某一层不准，而是输出契约写死了"永远 3 块"。**
   这直接堵死了用户描述的 North Star（"一元二次方程应该分成 知识 + 题型块1 + 题型块2 + …"）。
6. **建议做 Splitter V2**，但方式不是推翻重写，而是：**换输入（保留结构）+ 换契约（N 块 + 角色）+ 保留现有规则作为兜底**。

### 1.5 真正稳定的部分（应保留）

- `docutils.scan_paragraphs` 的段落编号模型（与 `xml_engine.fill_blocks` 对齐，是下游唯一契约）
- `toc_split.build_toc_blocks` 的**目录→正文 4 遍递减匹配**（精确 → startswith → 子串 → 去标点模糊）。鲁棒、确定、失败返回 `None` 而非崩溃。
- `auto_split` 的 `ratios` 保底——虽然粗糙，但保证永远有输出。
- `practice_splitter.refine_practice_split` 对"⚡基础速刷 / 🚀能力跃升 / 🌟思维挑战"这类成对标记的精修。
- `split_engine._protect_reading_spans` 对英语阅读语篇的保护（防止把一篇完形切成两半）。

### 1.6 最大结构性问题（按严重度）

**P0 — 输入丢结构。**
`docutils.py:62` 只取文本。下游所有分块只能在"纯文本流"上猜，而 DOCX 里白送的字号层次、样式、加粗、编号全被扔了。详见 §3。

**P0 — 输出契约写死 3 块。**
`auto_split` 无论输入结构如何，永远返回 `[知识精讲, 即时训练, 巩固练习]`。
这直接堵死 North Star：用户要的"知识 + 题型块1 + 题型块2 + …"是**变长块序列 + 角色标注**，不是固定 3 槽。

**P1 — 5 套并行、互不引用的边界识别器。**
同一类关键词/正则在 5 个文件里各写一份：

| 重复物 | 出现位置 | 份数 |
|---|---|---|
| `【题型N】` 正则 | split_engine:19 / hybrid_split:47 / xml_prep:24 / xml_engine:58 / runner:137 | 5 |
| 编号题正则 | split_engine:514,521 / split_candidates:34 / hybrid_split:49 / xml_prep:26 / xml_engine:57 / runner:136 | 6 |
| 分区关键词表 | split_engine:346 + :244 / split_candidates:17 / toc_split:12 / practice_splitter:16 / hybrid_split:59 | 5 套 |
| marker 映射（知识精讲/巩固练习） | split_engine:585,706 / toc_split:306 / hybrid_split:474 / llm_split:217 / split_candidates:277 | 6 |

改一个学科词要改 5 处——这正是 `docs/分块多学科设计.md` 自述的"数学英语多、语文政史地几乎为 0"的根因。

**P1 — 无回归基线。**
`docs/split_sample_labels.example.json` **只有 1 个样本**（且路径指向仓库外），指标是"±8 段容差"。历史文档里"100% 通过率" = 1 份文档、2 个检查点。7 个测试脚本中 6 个因 `sys.path` 指向 `tests/` 而非 `app/` 跑不起来，2 个还 import 了不存在的导出。
→ **现在无法量化"改好了还是改坏了"，这是做 V2 的前置阻塞项。**

**P2 — 分层语义混乱。**
- T0b 不是"降级"而是**短路**：`hybrid_split()` 除非 `total==0` 否则永远返回非空 list，而 `split_engine.py:742` 只判 `len>=1`。一旦 `enable_hybrid=True`，T1/T2 永远到不了。
- T1 异常被静默吞掉（`split_engine.py:938`）。
- 三套互不相通的置信度（规则分 0–100 / 候选分 45–98 / 相似度 0–1）无法横向比较。

**P2（范围外，但阻塞验证）** — `runner.py:66` 引用 `config.PS_FILL_CLASS/PS_FILL_1V1`，`jobs.py:182/189` 引用 `config.PS_IDEALIZE/PS_RENUMBER`，这些常量在 59 行的 `config.py` 里**根本不存在**。去 COM 改造只做了一半：`xml_*` 模块写好了，接线没改。分块算得再对，末端填充必崩。**本轮不处理，但它是后续做端到端验证的前置。** 另：仓库当前有未提交改动（`config.py`/`docutils.py`/`student_ops.py` + 4 个未跟踪的 `xml_*.py`）。

### 2.4 那"稳定"到底是什么？

综合 DEVLOG 与版本记录，**没有任何文档支持"0.4 分块分得好"**。V0.4 时代连分块模块都不存在，DEVLOG 对它只字不提分块。

用户记忆中的"稳定"最可能来自三件事的叠加：

1. **V0.8 目录（=V0.9）那条 TOC 路径确实稳**——`import re` 一把梭、确定性、零依赖、失败即降级、没有失败模式。这是"稳定感"的真正来源。
2. **V0.4 的稳是"开箱即用"的稳**（自带 Python 3.12、双击启动、无需配环境），不是分块质量的稳。
3. **V1.0 时代确实有"六份样本两刀边界全部落在正确位置"的记录**（`flash版/版本功能记录.txt` 第五节），但那是 Flash 1.1（2026-08-10），不是 0.8/0.4——而且样本只有 6 份、很可能是调参用的那几份。

### 2.5 是否值得恢复为 baseline？

**不值得整体恢复，但 T1 那条线应当保留并前置。**

- V0.8/0.9 的 `toc_split.py`（295 行）在 V1.0 被**改进**为 342 行：练习区角色分级（基础训练→即时训练 / 培优拔高→巩固练习）、编号规则细化、**删掉 70/30 硬切**。
- 归一化后，**当前仓库 `app/toc_split.py` 与 V1.0 版本内容完全一致**。
- 所以：T1 没有丢、不是退化、而且已经是最优版本。问题只是**它只覆盖 9% 的文档**（§1.3 实测）。

`split_engine.py` 的演化：V0.9 / V1.0 / flash版 / 当前仓库 全部 md5 相同（`eccd5a97…`），仅 V1.1 目录版有 9 行中文日志改英文。→ **自 2026-06-29 冻结，无退化也无演进。**

| 指标 | 数值 |

### 3.5 语料本身的偏差（必须纠正）

| 学科 | 文档数 | 占比 |
|---|---|---|
| 英语 | 139 | **60.7%** |
| 未标注/其他 | 81 | 35.4% |
| 数学 | 9 | **3.9%** |
| 物理/化学/语文/生物/历史/地理/政治 | **0** | 0% |

**验证语料与目标用户严重不匹配。** 历史结论"52 份里只有 4 份有可解析文字目录"（7.7%）是在这批以英语为主的语料上得出的；而数学类样本实测是 `题型 0 / 目录 0 / 短粗 27 / 超字号 14` —— 数学讲义几乎不写目录和【题型】，但排版锚点充足。**用现有 corpus 调参会持续把优化方向带偏。**

### 3.6 "以前偶尔分得特别好"的原因

不是某个版本更聪明，而是撞上了三种"文档恰好配合"的情况：
1. 文档**恰好有点线目录**（16.6%）→ T1 命中，边界天然正确；
2. 文档**恰好有模板 marker**（知识精讲 / 即时训练 / 六、巩固练习）→ 直接对位，几乎不会错；
3. 文档**恰好是"知识在前、题目在后"的干净两段式**→ T2-3 的"连续 3 段 q>k"正好落在真实切换点。

换言之：**历史上"分得好"是文档配合了规则，不是规则理解了文档。** 一旦文档是题型清单、分层训练、原卷+解析双半区，规则就失效。

## 4. D. 外部项目/论文/库研究：能迁移什么

### 4.1 调研过的方法

| 方向 | 代表 | 核心思想 | 是否适配本项目 |
|---|---|---|---|
| 词汇衔接 | TextTiling (Hearst 1997) | 相邻窗口词袋余弦 → 相似度谷值切分 | ❌ 段落中位 46 字符、29% ≤15 字符，词袋信号太稀疏 |
| 排序矩阵 + 分裂聚类 | C99 (Choi 2000) | 相似度矩阵 → 局部秩变换 → 密度最大化自顶向下分裂 | ❌ 同上；且它输出的是"话题段"，不是"知识/例题/练习"角色 |
| 话题模型 | TopicTiling / C99LDA (2012) | 用 LDA 主题 ID 替代词 | ❌ 需训练语料，短文本上主题估计不稳 |
| 语义分块 | SBERT / SemanticChunker / DeepTiling | 句向量余弦突变点 | ❌ **本项目已实证失败**（V0.9 DEVLOG：理科 99% 判 knowledge，已永久禁用）；且要下载 120MB 模型，违背离线/低成本 |
| 神经分割 + 句边界 | wtpsplit / SaT | 预测换行概率 | ❌ 解决的是"句子/段落边界"，不是"板块边界"；需 ONNX 运行时 + 模型 |
| 变点检测 | `ruptures` (PELT/Binseg/CUSUM) | 一维信号上的统计变点 | ⚠️ **思想可迁移，库不必引入**。可作为"题密度曲线"上的平滑/变点工具，但讲义段落数仅几百，自写 CUSUM 足够 |
| 版面分析（CV） | PP-DocLayoutV3、YOLOX-Layout、HiLEx (ICDAR 2025)、DocLayNet | 检测 Title/Text/Formula/Figure/Question 区块 | ❌ **方向正确但手段冗余**：它们是给**扫描图片**用的。我们拿到的是原生 DOCX，结构信息在 XML 里是**免费且精确的**，不需要 OCR/检测 |
| 教育文档层级抽取 | HiLEx 的 6 类层级 schema（Question_Paper_Area / Question_Block / Answer_Block / Instruction / Description） | 层级 + 角色标注 | ✅ **schema 思想值得抄**：先分区域，再标角色，最后才映射模板 |
| 规则+统计混合 | 本项目 T2 已有雏形 | 多信号加权 + 阈值 | ✅ 保留，但需重构为统一打分框架 |

### 4.2 真正能迁移的三条思想

1. **"结构优先，语义兜底"（来自版面分析领域的共识）**
   版面分析之所以有效，是因为它先用*物理层级*（字号/位置/样式）定骨架，再用语义分类内容。
   → 本项目应当完全照做：**DOCX 的字号/样式/加粗就是我们的"版面特征"，而且比图片版面分析精确得多、零成本。**

2. **层级 + 角色分离（来自 HiLEx）**
   不要把"切块"和"定角色"混成一件事。先得到一棵结构树（章→板块→子块），再给每个节点标角色（knowledge / example / practice / answer），最后才把角色映射到模板槽位。
   → 这正好解决 §1.6 的 P0"永远 3 块"问题，也正好接住用户的 North Star。

3. **边界评估用 WindowDiff 而非精确匹配（来自 Pevzner & Hearst 2002）**
   $P_k$ 会过度惩罚近似命中；WindowDiff 用滑动窗口比较边界数，更适合"±3 段"这种容忍度。
   → 建议 V2 的评估指标同时报：锚点命中率（±3）、WindowDiff、块数正确率、角色正确率。

### 4.3 明确不适合我们的

- **任何需要下载模型的方案**（SBERT / SaT / Layout 检测模型）——违背"基层老师、离线、零持续成本"。
- **任何基于词袋/句向量的话题切分**——讲义文本太短、公式在段外。
- **OCR / 图片版面分析**——我们拿的是原生 DOCX。（例外：若将来支持 PDF/扫描件输入，PP-DocLayout 系列才是正确工具，届时可复用同一套"层级+角色"schema。）
- **LLM 进入运行链路**——用户已明确不希望。可作为**研发期标注助手**（生成候选 golden 再由人确认），不进产品。

## 6. F. 推荐的下一代架构：Splitter V2

### 6.1 为什么不沿用 T0/T1/T2

现有分层的问题不是层数不对，而是**两件事被混在一起了**：

- T0a/T0b/T1/T2 是**"方法降级"**（按算法先进程度排序）
- 但真正需要的是**"信号优先级"**（按信号可靠度排序）

结果就是：最可靠的信号（排版）被排除在外，最不可靠的方法（语义）被放在最高优先级；且 T0b 会因"永远返回非空"而**短路**掉后面所有层。

V2 的原则：**不要按"方法先进度"分层，要按"信号可靠度"分层；每一层都必须能给出置信度；层与层之间是"叠加证据"而不是"互相替代"。**

### 6.2 三阶段架构（推荐）

```
┌─ Stage 1：结构抽取（Structuring）───────────────────────
│   输入：DOCX 原生 XML（保留 style / 字号 / 加粗 / 编号 / 图片 / 表格）
│   输出：StructDoc = 有序 Block 序列 + 每个 Block 的排版特征向量
│   特点：纯解析，零判断，100% 确定性，永不失败
└───────────────────────────────────────────────────────
                          ↓
┌─ Stage 2：层级与角色标注（Labeling）────────────────────
│   2.1 骨架层：字号分层 + 样式 + 分隔线 → 章节树（L1/L2/L3）
│   2.2 板块层：已知板块词表 + 模板 marker → 板块节点（知识/训练/巩固/总结/答案）
│   2.3 题型层：题型N / 角度NN / 【题型】 → 题型节点
│   2.4 角色层：段落级 question/knowledge 打分 → 每个 Block 的角色 + 置信度
│   2.5 双半区检测：重复标题 / 答案标记 → 剥离答案区
│   输出：带角色 + 置信度的结构树（块数 N 可变）
└───────────────────────────────────────────────────────
                          ↓
┌─ Stage 3：模板映射（Mapping）───────────────────────────
│   把 N 个角色块映射进模板槽位（1v1 三槽 / 班课槽位）
│   规则：角色相同则合并；无法归类则按置信度就近合并；
│         可配置策略（保守=合并到 3 块 / 激进=按题型块展开）
│   输出：最终 blocks（与下游 fill_blocks 契约一致）
└───────────────────────────────────────────────────────
```

### 6.3 与 North Star 的兼容性（关键设计点）

Stage 2 输出的**结构树 + 角色**是中间表示（IR），Stage 3 是**可插拔策略**。这样：

- 现在：Stage 3 = 保守策略 → 行为与现有引擎一致（永远 3 块），不破坏现有产品。
- 未来：加一个 `example_promotion` 策略 → 题型块内第 1 题前移为例题，其余下沉为练习。
- 未来：加一个 `practice_promotion` 策略 → 例题过多时保留最典型一道，其余下沉。

**North Star 是 Stage 3 的一个策略插件，不需要改 Stage 1/2。** 这正是"不留死路"的架构保证。

### 6.4 各层具体设计（V2）

| 层 | 信号 | 输出 | 置信度 | 覆盖率（实测） |
|---|---|---|---|---|
| S1 结构抽取 | XML 直读 | Block + 特征向量 | 1.0（纯解析） | 100% |
| S2.1 骨架 | 字号分层（相对正文）+ 样式名 + 分隔线 | L1/L2 章节边界 | 高（0.8~0.95） | 56.3% |
| S2.2 板块 | 板块词表 + 模板 marker + 中文序号 | 板块节点 | 高（0.85~0.95） | 与现有 T1 同级或更广 |
| S2.3 题型 | `题型N`/`角度NN`/`【题型】` + 字号层 | 题型节点 | 中高（0.7~0.9） | 显著高于现有 15.3% |
| S2.4 角色 | 段落 question/knowledge 打分（沿用现有 `_QUESTION_SIGNALS`，改为**归一化密度**） | 每块角色 + 分 | 中（0.5~0.8） | ~100% |
| S2.5 双半区 | 标题重复 + 答案标记 | 剥离答案区 | 中（0.6~0.85） | 59.4% 受影响 |
| S2.6 变点兜底 | 题目密度曲线 CUSUM（**相对阈值**，替代现有绝对阈值） | 无结构文档的边界 | 低（0.3~0.6） | 兜底，剩余 ~20~40% |
| S2.7 比例兜底 | `ratios=(0.5,0.85)` | 保底 | 0.1 | 永不失败 |

**关键改进点：**
1. **字号分层是主判据，bold 只做确认**（避免 §3.4② 里 51 处 bold 只有 10 处真标题的误判）。
2. **兜底阈值改为相对自适应**：现有 T2-3 用"连续 3 段 q>k 且 q≥2/1/1"的绝对值，在 46 字符短段落上噪声大；改为"密度滑动平均 + 相对跃变"。
3. **统一置信度到 0~1**，所有层可横向比较，Stage 3 才能按置信度决策。
4. **5 套关键词收敛为 1 份配置**（`split_profiles/*.json`，可复用 `docs/分块多学科设计.md` 已有的学科画像思路）。

### 6.5 不改动的部分（明确保护）

- `split_engine.auto_split` 的**对外签名与返回契约**（`[{marker, start, end}]`）保持不变 → 下游 `runner` / `fill_blocks` 零改动。
- `toc_split.build_toc_blocks` 的 4 遍递减匹配逻辑原样保留，作为 S2.2 的一个信号源。
- `practice_splitter.refine_practice_split` 原样保留，移入 Stage 3。
- `_protect_reading_spans` 原样保留。
- 所有兜底行为保留（宁可退回 V0.4 的 50/85，也不能没输出）。

## 8. H. 建议的验证 corpus 与成功指标

现有 corpus 61% 是英语、数学仅 9 份、物化 0 份 —— **不可用于调参**。建议重建分层语料 **60 份**：

| 无结构流式 | 10 | 验证兜底质量 |

标注格式（在现有 `split_sample_labels.example.json` 上扩展）：

### 8.2 成功指标（分级）

| 级别 | 指标 | 现状（基线） | V2 目标 |
|---|---|---|---|
| 主指标 | **两刀都准**（边界落在锚点 ±3 段内） | **14.4%** | ≥ 55% |
| 分指标 | 边界1 命中率 | 63.1% | ≥ 80% |
| 分指标 | 边界2 命中率 | 14.4% | ≥ 60% |
| 结构指标 | **块数正确率**（预测的 N 块 == 人工标注 N 块） | 无（永远 3 块） | ≥ 50% |
| 语义指标 | 角色正确率（knowledge/example/practice 三分类） | 无基线 | ≥ 70% |
| 学术指标 | WindowDiff（越小越好） | 无基线 | 建立基线后相对下降 ≥ 30% |
| 健壮性 | 崩溃率 / 空输出率 | 0%（现有优点） | **必须保持 0%** |
| 学科均衡 | 数学子集上的两刀准确率 | 未知 | 单独统计，不得低于英语子集 10 个百分点 |

**红线圈定：健壮性指标一票否决。** 任何让"崩溃率 > 0"或"无输出"的改动都不接受。

## 10. 最终建议

1. **不要去找回 0.8。** 它不是一个被弄丢的更优算法；它的改进版已经在仓库里，而且只覆盖 9% 的文档。用户感受到的"稳定"来自"文档恰好配合规则"。
2. **真正的瓶颈是输入丢结构和输出写死 3 块**，不是算法不够先进。
3. **Splitter V2 值得做**，形态是：
   - Stage 1 保留 DOCX 结构（约 30 行改动，最高性价比）
   - Stage 2 层级+角色标注，输出**变长、带角色、带置信度**的结构树
   - Stage 3 可插拔模板映射（North Star 作为未来策略插件）
   - 现有 `auto_split` 整体降级为兜底层，对外契约不变
4. **先建评估基线，再动代码。** 60 份分层语料 + golden 标注是 E0，做完它才有资格谈"变好"。
5. **把 5 套重复关键词收敛为 1 份可配置画像**，这是多学科扩展的唯一可持续路径。
6. **不引入任何需要下载模型的依赖，不把 LLM 放进运行链路。** LLM 只用于研发期生成标注初稿。
